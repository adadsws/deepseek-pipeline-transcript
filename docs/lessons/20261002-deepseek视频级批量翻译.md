# DeepSeek 视频级批量翻译复盘

## 结论

- 对 167 句真实字幕做 2×2 对照后，关闭思考并按整视频请求是当前最省 token 的组合：4,178 总 token，对比“开思考＋10 句一批”的 52,926，下降 92.1%。
- GPU 转录适合严格单路，网络翻译适合在多个视频之间并发。批处理因此采用流水线：每完成一个视频的转录就立即提交翻译，同时转录下一个；每个视频仍需完整校验后才原子发布。
- 正常视频一次请求；超长视频必须在首次请求前按固定预算切分。请求失败、空正文、漏键或 JSON 无效后不得自动二分、修复续问或补发。

## 实现经验

1. 仅把配置中的 `request_level_auto_retry` 写成 `false` 不足以保证只请求一次。必须同时绕过上游 tenacity、将 OpenAI SDK 的 `max_retries` 设为 0，并把 agent 格式修复循环改为单次校验。
2. DeepSeek JSON 模式要求提示词中出现字面量 `json`。仅传 `response_format={"type":"json_object"}` 会返回 400，因此批处理路径会补入明确的 JSON 输出指令。
3. 多视频并发后，usage 回调和请求日志上下文不能继续用进程级全局变量，否则不同视频会串账。线程局部上下文可保持每视频 token、费用和日志归属正确。
4. 缓存键需要包含模型原键、路线版本、思考模式、输入/输出预算和提示词指纹，避免旧的 10 句缓存被整视频路线误用。
5. “一次请求”与“一个 HTTP 调用”必须分别验证。测试既要断言业务层只调用一次，也要检查实际日志中的 `thinking=disabled`、`reasoning_effort=none`、JSON 模式、输出上限和 reasoning token 为 0。

## 测试方法

- 四组测试必须使用完全相同的源字幕、模型和提示词，只改变思考开关与分块方式，才能区分两项变量各自的影响。
- 除 token 和费用外，还要检查请求数、耗时、`finish_reason`、键集合、空译文和漏句。翻译具有随机性，不能用逐字相同率代替人工质量抽查。
- 首次真实生产路径冒烟暴露了 JSON 字面量约束；修正后 5 句字幕以 1 次请求完成，共 388 token，其中思考 token 为 0。这类小规模付费冒烟应放在全量处理之前。

## 保留边界

- GUI 保持上游 10 句分块行为，视频级路线只在 `VIDEOCAPTIONER_EXECUTION_MODE=batch` 时启用。
- 用户在轮末主动选择重试不属于自动重试；此时可以复用已经完整成功的旧缓存或超长视频预拆分块，但不能缓存、发布不完整整视频响应。
- 固定上游源码不做直接修改，所有适配继续放在项目补丁与批处理编排层，便于后续对比和升级。
